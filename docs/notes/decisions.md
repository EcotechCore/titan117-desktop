## 1. Scope

- **V1 is everything in the [feature map](brainstorming-feature-map.md)** (feature map decision 18). No public launch until the whole product works well.
- **Not doing:** agents hosted around the clock on our servers; sign-in with chat subscriptions; bypassing CAPTCHAs, paywalls, logins or bot detection. Our own background features (search, crawling) respect site terms; where the user points an agent at a site, it's their choice, with a warning (§29).
- The work is split into phases ([§10](#10-build-plan)), not into releases.

## 2. Local-first

- The Titan engine runs on the user's laptop: agents, tools, memory, documents, app data. When the laptop is off, agents stop; scheduled work catches up on the next launch.
- Our cloud is small: accounts, plans, credits, devices, remote commands, and what users choose to share.
- Company data never reaches our servers unless the user shares it or sends it to a cloud model they picked.

## 3. Models and payment

- **Model sources:** local models (llama.cpp, built in), OpenRouter, and the user's own Anthropic, OpenAI or Google key.
- **Paying for cloud models:** our credits, or the user's own key. Both need a subscription.
- **Subscription first, then credits** to top up (Lovable's model). Plans, prices and credits are decided in [§13](#13-pricing).
- **No sign-in with chat subscriptions** (Claude Pro or Max, ChatGPT Plus or Pro, Gemini plans): Anthropic's terms ban it outside its own apps and it blocks such tools; OpenAI's position is unclear. Revisit only if a provider officially allows it. Not to be confused with [§20](#20-your-own-coding-tools): running the vendor's own tool that the user signed into themselves.

## 4. Open-source reuse

- MIT, Apache 2.0, BSD: copy and adapt, keep notices, list them in the third-party licences file.
- GPL, AGPL: ideas only, or run unchanged as a separate program.
- No licence or non-commercial: ideas only.
- Every project we take code from gets a row in a sources list (project, licence, what we took, commit).

## 5. Web search

- Default: a paid search API through credits: **OpenRouter's search tool**, through our credit proxy (decided in §14 and §12).
- Option: the user's own key (Brave, Tavily, Exa; ~~Serper~~ dropped 15 Nov 2026, §44).
- ~~Free mode, opt-in only, built on ddgs or open-webSearch~~ Dropped 8 Nov 2026: it scraped other search engines in the background. Replaced by **search in the browser on the user's request** (§30).

## 6. Repositories and docs

- `titan117-web`: Next.js web app, the Convex backend, and `@titan117/shared` (protocol, types, generated Convex client), published privately with versions.
- `titan117-desktop`: Electron shell, the engine, agents and tools; installs `@titan117/shared` at a fixed version.

## 12. Tech stack

Decided 16 Oct 2026.

- **Desktop shell: Electron.** The same Chromium on Windows and macOS, so artifacts, previews and sidebar apps look the same everywhere. Tauri stays the template for desktop apps that users build (feature 6.4).
- **Engine runtime: Node**, the one inside Electron (a utility process), so there's no second runtime to ship. Playwright and our other tools target Node.
- **Payments: Stripe directly**, not Clerk Billing. Clerk Billing is in beta and today is USD only, with no VAT handling, no 3D Secure (needed for many EU cards) and no usage-based credits. With Stripe: subscriptions, one-time credit top-ups, Stripe Tax for EU VAT, any currency. Only the payment webhook writes plans and credits (guardrails §3). Stripe Tax or a merchant of record is decided before beta.
- **Coding engine: OpenCode** (MIT), in headless server mode inside the engine. It releases very often and sometimes regresses, so we **pin a version**, put it behind **our own adapter interface** (so it can be swapped), and run **contract tests** on every upgrade. Its permission prompts become our approvals.
- **Credits path: our proxy** (decided 17 Oct 2026, replacing the sub-key plan of 16 Oct).
  - **One OpenRouter account**, funded by Ecotechcore (starting balance about €1,000, auto-top-up and a low-balance alert). **One secret key**, kept only in our server's environment variables, never in the desktop app.
  - The desktop engine calls **our endpoint** with the user's sign-in token. The endpoint checks the user and their credits, forwards the request to OpenRouter with our key, **streams** the answer back, then **deducts the credits** in the Convex ledger.
  - The endpoint is a small **streaming route on Vercel** (long streams don't suit Convex actions); Convex keeps the ledger and the rules.
  - **Prompts pass through but are never stored**; the privacy policy says so. Documents and memory stay on the laptop.
  - **Credits running out mid-request:** a minimum balance is checked before a request starts; a small overdraft is allowed and settled by the next credits.
  - The same proxy carries OpenRouter's web search. ~~AI video and image providers (fal.ai or Replicate)~~ Changed 8 Nov 2026: every paid service other than OpenRouter is the user's own account (§31).
  - **Rate limits and abuse checks** live in the proxy (guardrails §2, §3).
  - **Confirmed by OpenRouter, 8 Nov 2026:** one funded account whose credits subscribers use through our backend is allowed, with the key kept on our server, caps on the account and per-user limits ([their answer](vendor-answers/openrouter-2026-11-08.md)).
  - **Own keys stay direct:** a user's own OpenRouter, Anthropic, OpenAI or Google key is stored in their OS keychain and the engine calls the provider directly, with no proxy and no credits. They pay us only the subscription (own keys need a paid plan, decisions §13).
  - **Later, optional:** per-user OpenRouter sub-keys with spending limits, if traffic grows enough that carrying every stream becomes costly.

## 17. Offline use and licence

Decided 17 Oct 2026.

- **Subscription required.** Every use of the app needs an active plan; there's no free mode.
- **Signed licence lease.** When online, our server issues a licence signed with our private key: the user, the device, the plan, what it includes, and an expiry. The app checks the signature with the public key built into it, and renews the lease quietly in the background whenever it's online.
- **Offline:** the app works with local models, local tools and local data until the lease expires. The offline period is **14 days** (confirmed 17 Oct 2026). Offline mode is part of V1 (features 1.22–1.24). A warning shows from 3 days before expiry: "Connect to the internet to keep using Titan117".
- **When the lease expires, the subscription ends or payment finally fails, the app locks:** a full-screen sign-in and renew screen replaces the workspace. No agents run.
  - **Running tasks** are paused at a checkpoint, never killed halfway.
  - **The user's own files** (documents, exported artifacts, project folders, generated app code) stay on disk and are theirs; the app never deletes or encrypts them.
  - **"Export my data"** stays available on the lock screen (chats, memory, artifacts), for GDPR and trust.
- **Payment failures:** Stripe retries for a few days (dunning) before the subscription ends; the app warns during that time.
- **Clock tricks:** the app stores the latest time it has seen and the server time from the lease; setting the clock back doesn't extend the lease.
- **First sign-in needs internet**, once; then the session stays in the OS keychain.
- **Online-only features** (cloud models, own keys, web search, remote control, publishing, sharing, sync, buying credits, downloading components) show "Needs internet" cards offline; usage reports, sync and notifications queue until the connection is back.
- **Honest limit:** a desktop app can be tampered with by a determined person. That's acceptable: the paid value that costs us money lives on our server.

## 21. How the app evolves

- **7 Nov 2026, in V1 (features 18.1–18.9):** Titan117 is built like an operating system. The **core** (engine, permission and approval layer, model router, credits and metering, licence lease, sync, update channel) is fixed, signed and changed only by our releases. **Everything above it** (agents, skills, tools, sidebar apps, automations) can be added, changed and removed by users and by Titan.
- When a user needs something we didn't build, they ask Titan; it plans the add-on, shows what it will create and what it may access, and builds it after their OK, using the agent builder (§4 of the feature map), the coding engine and the app builder. Add-ons are packages with a `titan.json` manifest, run in the marketplace sandbox, have versions and rollback, and can be shared on the marketplace.
- **Agents never modify the core** on the user's computer: no writing to the app's files, its permission, credit or licence settings, or its update channel. Why: an agent that could edit the permission layer could switch off every safety check (one poisoned web page would be enough); it would break code signing and auto-update; it would make the licence and metering trivially bypassable; and every user would run a different app we couldn't support.
- **Safe mode:** if the app can't start, or keeps failing after an add-on changed, it starts with add-ons off and offers to roll back or remove the one that broke it.
- **Core fixes come from us:** Titan can attach a write-up and a suggested fix to an error report (§22), with the user's consent; we review it and ship it to everyone through auto-update.
- Plan: agents and skills on request in phase 11; tools, sidebar apps, add-on packages, safe mode and the core-is-off-limits checks in phase 16; the fix loop in phase 18.

## 23. Security model

- **7 Nov 2026:** security is written in [`docs/security.md`](../security.md) in two parts, **protecting our users** (their data, laptop and account) and **protecting us** (credits, subscriptions, our keys, our releases, our portal). Rules with their enforcement are in the guardrails.
- **Remote control** (users): off by default, switched on per laptop; **two-factor required** to switch it on (Clerk, a passkey first); pairing confirmed on the laptop; **laptop-only approvals** for deleting, payments, sending files or data out, installing add-ons and changing permissions (or remotely after a second factor, if the user chooses); alerts on every remote task; "Revoke all devices". **As easy as possible:** the one-time setup is part of the setup checklist, and everything else can be approved anywhere.
- **End-to-end encryption is V1** (feature 9.5), with the key design in the architecture: device keys made on each device, pairing confirmed by a matching code, ciphertext only in Convex, key rotation when a device is removed. Chat channels can't be end-to-end, and the app says so.
- **Network policy per task** (after Claude Code, Codex, Cursor and the browser agents): site lists, ask before a new site once private data was read, block requests carrying private content.
- **Chat channels:** one-time-code linking, private chats only in V1; **the web and phone apps can do everything a channel can.**
- **Product owner portal** (us): a separate app in its own repo (`titan117-pop`, §6) for the owner and employees, with error reports, accounts, credit corrections, kill switches and releases; two-factor required; every view logged.
- **Our money and keys:** balance and entitlements only on the server, the proxy checks before every call, a signed licence lease, device limits on the server, hard spending caps on every paid provider. A cracked app only unlocks local features (accepted, §17).
- **Our releases** (the owner's development process): cloud code signing, a second signature for updates, branch protection, pinned GitHub Actions, a second approval to publish, two-factor everywhere.
- **Process:** `security.txt` with `security@titan117.com`; an incident checklist with a rotation step per key; an **external penetration test before the public beta** (phase 18).
- **Accepted risks:** malware already on a user's laptop; cracking the licence for local features; chat channels not being end-to-end; users approving a harmful action they were shown; vendors changing their terms.

## 25. GitHub identity

- **8 Nov 2026:** when an agent commits, pushes, opens a pull request, forks or publishes, it does it **as the user**, the way Cursor, VS Code and Claude Code work on your own repos. The user owns and answers for what lands in their repos, and repo owners see a person they know, not an unknown bot. There is **no `titan117[bot]` acting in users' repos**.
- **Local git:** the user's own git setup on the laptop (name and email, Git Credential Manager or SSH keys). Commits are authored by the user. Each agent commit adds a `Co-authored-by` trailer naming Titan117, so the AI's part is visible in the history; the user can turn it off in settings.
- **GitHub actions** (open a pull request, fork, create a repo, publish a marketplace item, 10.6 and 13.7): the user clicks **Sign in with GitHub**, approves our GitHub App through GitHub's **device flow**, and picks which repos it may use. The app gets a **user access token**. GitHub's documented behaviour (checked 8 Nov 2026 on docs.github.com):
  - Actions are attributed to the user: the user's avatar with the app's small badge in the GitHub UI, and the user as the actor in audit logs.
  - The token has only the permissions both the user and the app have, on only the repos both can reach.
  - The token expires after 8 hours; its refresh token lasts 6 months.
  - The device flow needs no client secret, so nothing secret ships in the app.
- **The GitHub App** is registered under the **EcotechCore** organisation (its install screen reads "by EcotechCore") and asks for the smallest set of permissions the features need, listed in the phase 7 spec. It is used only for user access tokens, never with its own installation identity in users' repos.
- **Tokens stay on the laptop**, in the OS keychain (guardrails §8). They never go to Convex, our servers, logs or error reports. A coding task started from the web or phone runs on the laptop with the laptop's token.
- **Approvals:** pushing, opening a pull request, forking and publishing are outward actions and go through the approval screen (4.5) unless the user allows them for that repo. Agents never force-push, push to a protected branch or merge without the user's OK.

## 38. Phase 1 engine choices

Made on 14 Nov 2026 while building phase 1, each because the build needed an answer. The owner confirmed item 6 the same day and asked that the others be what the industry does, or better; each was checked against that and the result is under the list. Any of them can be reversed without touching the rest.

1. **The engine is its own process** (an Electron utility process) and the window reaches it only through the local API: HTTP on `127.0.0.1`, a per-install token on every request, events as a stream. A request from any origin but the window's own is refused, and so is a host name that isn't `127.0.0.1` or `localhost`.
2. **The window's page is served from our own scheme, `titan117://app`,** instead of `file://`, so it has a real origin the local API can check.
3. **Allowed folders change only through the folder dialog** shown by the shell. The local API has no route for it, so no page, agent or tool can widen its own access. The app's install folder, its data folder and credential folders (`.ssh`, `.aws`, `.env`, other tools' logins) are refused even inside an allowed folder.
4. **Risk levels:** `read` runs without asking inside allowed folders; `write` waits for the user, who may answer "always in this task"; `external` always asks and is answerable only on the laptop. Phase 1 ships three tools (list a folder, read a file, write a file); the rest arrive with Titan in phase 3.
5. **SQLite through Node's built-in driver (`node:sqlite`)**, not better-sqlite3: no native module to rebuild for Electron, and it has full-text search (FTS5). Revisit if we need something it lacks.
6. **Our own small OpenRouter client** (one streaming call, OpenAI-compatible) instead of the Vercel AI SDK for now, behind one provider interface. The SDK can sit behind the same interface when the user's own Anthropic, OpenAI and Google keys arrive (phase 2) or with MCP (phase 3).
7. **Local models come from Hugging Face**, downloaded by node-llama-cpp with no account, and only models whose licence we checked are listed (§33). The first three are Qwen2.5 1.5B Instruct, Qwen3 4B and Qwen2.5 7B Instruct (all Apache 2.0). Qwen2.5 3B is left out: its licence is for research only. llama.cpp is never built from source on the user's laptop.
8. **llama.cpp is started in a side process first.** Its prebuilt Windows binaries crash the process that loads them when the Microsoft Visual C++ runtime is older than 14.40 (found on the development laptop, which had 14.36). The engine now reports "local models can't start on this laptop yet" instead of crashing. The check runs in the background, because the first start can take close to a minute, and the window doesn't wait for it. **Phase 5 must ship the runtime with the app** (or install it), so users never see this.
9. **The development OpenRouter key** is read from the repo's local `.env` only when the app runs from source; a packaged app never reads it. Keys move to the keychain in phase 2.
10. **The shell sandbox** (open decision 2) is needed when the shell tool is built, in phase 3, not in phase 1: phase 1 has no shell tool.
11. **Budgets per task:** 25 steps, 15 minutes of working time (waiting for the user doesn't count), $0.50 of provider cost, and the same call three times in a row counts as a loop. Dollars become credits in phase 2.

**Against common practice:**

- **As the industry does it:** a local server on `127.0.0.1` with a token and an origin check (items 1 and 2: VS Code, Jupyter and Ollama's desktop apps work this way); read, write and external risk levels with "allow once" or "always" (item 4: Claude Code and Codex); a custom app scheme instead of `file://` (item 2: Electron's own security advice); llama.cpp through node-llama-cpp with GGUF files from Hugging Face (item 7: LM Studio, Jan and Ollama use the same files); budgets with step, time and cost caps (item 11).
- **Stricter than most:** folders can be widened only by a dialog the user answers, never by the API (item 3); credential folders are refused even inside an allowed folder; llama.cpp is tried in a side process before the engine loads it (item 8).
- **One place we differ:** item 5. Most Electron apps use better-sqlite3. Node's built-in driver is newer and Node still labels it a release candidate; we use it because it needs no native build per Electron version. All database access sits in one file (`src/engine/lib/db.ts`), so moving to better-sqlite3 is a small change if the built-in driver gives trouble. Revisit before the public beta.

## 39. Desktop sign-in and the licence lease

Decided 15 Nov 2026 while building phase 2, following §17 and architecture §6; each choice is what the industry does or stricter.

1. **Sign-in through the system browser with a loopback redirect** (RFC 8252, the OAuth guidance for native apps): the app listens for a moment on `127.0.0.1` at a random port and opens `/desktop/sign-in` in the user's own browser, where they're already signed in with Clerk. They confirm, and the page hands a one-time code back to `127.0.0.1` only. No password is typed into the app, and nothing depends on a custom URL scheme (architecture §6 said "deep link"; the loopback is the same flow without registering a scheme with the OS, which is fragile on Windows). GitHub's and Google's command-line tools sign in the same way.
2. **PKCE (RFC 7636, S256):** the code is bound to a secret only the app that asked knows, so a code seen by anything else is useless. A code lives five minutes, works once, and is burned by a wrong verifier.
3. **The app gets its own device token**, not a Clerk session: a random 256-bit token kept in the OS keychain (Electron's `safeStorage`), sent as a bearer token to the lease endpoint and the credits proxy. We store only its SHA-256, so a copy of our database can't act as anyone's laptop. Signing a device out on the account page stops the token at once; the app locks at its next lease check. Each device is a row in `devices`; a plan's device limit (2, 3 or 5) is checked when a device signs in.
4. **The lease is signed with ECDSA P-256 / SHA-256** (Web Crypto in the Convex runtime). The private key is only in the Convex environment (`LEASE_PRIVATE_KEY`); the public key is built into the desktop app. A lease names the user, the device, the plan, how many devices it allows, when it was signed and when it expires.
5. **Expiry:** 14 days from signing while the plan renews (§17's offline period); for a plan that's cancelled or whose payment is failing, never later than the plan's last usable day; with no plan, at once (the app locks and shows "choose a plan"). The app renews it quietly whenever it's online.

## 40. The user's own API keys

Decided 15 Nov 2026 while building phase 2 (features 2.9, 11.5; architecture §5).

1. **Where keys live:** in the OS keychain on the laptop (Electron's `safeStorage`), held by the shell and handed only to the engine; never in our cloud (§32) and never back to the window, which can only ask which providers have a key. ## 43. Phase 3: Titan's tools, memory and the network policy

Made on 15 Nov 2026 while building phase 3 (Titan and memory), each because the build needed an answer. Like §38, they follow what the industry does, or are stricter. **The owner confirmed them on 15 Nov 2026** (items 1 and 10 after choosing between options); any of them can be reversed without touching the rest.

1. **The shell sandbox (open decision 2).** Every command runs in its own process, in an allowed folder, with a time limit (2 minutes by default, at most 10), capped output and a **scrubbed environment**: only a short list of harmless variables (`PATH`, the user's folders, language), never keys, tokens or Titan117's own settings. **On macOS** the process also runs inside Seatbelt (`sandbox-exec`, as Codex does, its base rules adapted under Apache 2.0): it may read the disk except credential folders and our own core, write only in the allowed folders and its temp folder, and reach the network only after the user approved a command that needs it. **On Windows there is no OS sandbox**: the approval rules carry the weight, as in Claude Code on Windows. **The owner confirmed this on 15 Nov 2026** (option A), after comparing it with a restricted Windows user as Codex does (B), AppContainer (C) and Windows Sandbox or a virtual machine (D). Not planned before the beta; D may come as an extra for risky jobs with phase 7's containers and virtual machines.
2. **Which commands ask (decisions §33.1).** Read-only commands from a short list (list, read, search, `git status`, `--version`) run at once. Everything else asks, with "Allow once" or "Always allow `<program>` in this folder" (`git commit`, `npm install`: per subcommand for tools like git and npm). **Always asks**, never "always": deleting (`rm`, `del`, `Remove-Item`, `git clean`), admin (`sudo`, `runas`), disks (`format`, `diskpart`, `dd`), system changes (registry, services, scheduled tasks, firewall, stopping programs), saved logins (`.ssh`, `.env`, credential stores, browser cookies) and force-pushes. Anything that hides what runs (a subshell, an encoded command, piping into a shell) asks at least. Unknown means it asks.
3. **Scripts (4.10, 3.11).** `run_code` runs JavaScript on the app's own Node (Electron's, so nothing to install) or Python when the laptop has it (built-in Python comes with phase 5, feature 1.15). A script calls Titan's tools with `titan.call(name, input)` through the local API with a **token of its own**, valid only while its task runs and only for tool calls; every call goes through the same permission layer, is logged "from a script", and a script can't start another script.
4. **The browser (3.10)** is Playwright (Apache 2.0) driving the laptop's own **Edge or Chrome**: nothing to download, and Edge is on every Windows. It has its own profile in the app's data folder, so sites the user signs into stay signed in. No stealth, no CAPTCHA solving: a CAPTCHA hands over to the user (§29). A control labelled publish, post, send, pay, buy, order, delete and the like asks first, every time, laptop-only; Discord isn't automated at all; sites on the "forbids automation" list warn first and remember the answer per site. Downloads come with phase 4.
5. **The network policy per task (security.md A3).** Every request a tool makes goes through one gate. A task's site list starts with the sites its messages name; a new site is added quietly until the task has read something private (files, command output, connector results, transcripts); after that a new site asks first ("Open example.com? This task has read …"), laptop-only. Requests carrying private content are blocked whatever the site: **passages are kept as fingerprints** (32 letters and digits in a row, hashed, never the text) and checked in addresses, form fields and uploads, also when URL-, base64- or hex-encoded; keys and tokens are blocked whatever their length. A networked command or script carrying private content is refused **before the user is even asked**. In the browser, the page the task opens is checked as a navigation; what the page loads by itself (images, scripts) only for private content, so the hidden-image trick is caught without asking about every CDN. Pages the browser reads are not counted as private, so browsing alone doesn't make every next site ask; signed-in pages are the gap, revisited with the folder agent (phase 6).
6. **Memory (3.2-3.4)** is in the local database with full-text search. Kinds: company profile, preference, fact, note. Scopes: `shared` (every agent) or one agent's own; an agent reads shared memory and its own, so the QA agent can't read the finance agent's notes. Every memory says who wrote it and from which task; the user can add, edit and delete any of them. At the start of each run Titan gets the profile and preferences plus the memories that match the request. Those passages may not leave in a web request, but placing memory in the prompt doesn't make the task private (otherwise every task would ask before every site). Saving runs without asking while the task has seen only the user's own words; once it has read outside content, saving asks, so planted text can't quietly become a memory (guardrails §5). Keys are redacted before saving.
7. **Skills (3.5)** are Markdown files with a short header (name, description, who wrote it, when) in the app's data folder, which agents' file tools can't reach: a skill can be written only through `skill_save`, which always asks (a skill is a standing instruction). Titan sees the list of skills and reads one before doing that kind of task; the user reads, edits and deletes them in Memory.
8. **Past tasks (3.13)** get a record when a task that used tools ends: the goal, the steps, what failed, the result, the files and sites. Built from the activity log, with no extra model call. The three most similar records go into the next similar task's instructions, marked as data; the user can search and delete them. Local only (§32).
9. **Connectors (3.6)** are MCP servers the user adds: a program on the laptop or an `https://` address, through the official MCP TypeScript SDK (MIT). Their secrets (tokens, environment variables) are in the keychain like API keys; a program connector gets the shell's scrubbed environment plus its own secrets only. A connector tool that says it only reads and whose name only reads runs at once; one that sends, posts, deletes, pays, archives or merges (by name or its own "destructive" flag) always asks, laptop-only; everything else asks with "always in this task". Output is private and marked as data. Specific services (Gmail, Outlook, Google) with our own sign-in stay as planned in §27; until their verification is done, users connect them through their providers' own MCP servers.
10. **Speech (3.14).** Speech to text is **Whisper base** (Apache 2.0, about 80 MB, downloaded from Hugging Face the first time) through transformers.js (Apache 2.0) and ONNX Runtime (MIT), on the laptop. Text to speech uses **the operating system's own voices** (Windows' speech synthesizer, macOS `say`): free, local, nothing to download. **Kokoro is not used, by the owner's decision (15 Nov 2026):** its pronunciation step needs eSpeak NG, which is GPL-3.0, and Titan117 is a paid product whose code must never have to be published, so we don't ship GPL software at all, not even as a separate program. A more natural voice is revisited later: cloud voices through credits (opt-in, §34), or a local model with no GPL inside. **Lesson:** check what a package bundles, not only its declared licence (Kokoro's JavaScript package says Apache 2.0 and compiles eSpeak inside). The window has a microphone button (the only browser permission the window gets, for our own page only) and "Read aloud" on replies.
11. **The check (roadmap phase 3)** runs as `pnpm eval:titan` against a real model through OpenRouter: ten everyday tasks and three prompt-injection scenarios, with the harness playing the user (approving in the everyday tasks, denying everything in the injection ones) and checking what happened on disk and on the network. The deterministic injection suite (a fooled model that obeys planted text, plus a real-browser hidden-image test) runs in CI with the other tests.

**Against common practice:** the approval model, the always-ask list and per-command "always" are what Claude Code and Codex do; Seatbelt on macOS is Codex's approach; Playwright on the installed Chrome or Edge is what Claude in Chrome-style and browser-use agents do; MCP for connectors is the standard. **Stricter than most:** private content is blocked from leaving even when the user approves the request, and a new site asks after private data. **Weaker than Codex:** no OS sandbox on Windows (item 1), the same as Claude Code there; confirmed by the owner.

## 44. Phase 4: web search and artifacts

Made on 15 Nov 2026 while building phase 4 (web search and artifacts), each because the build needed an answer. Like §38 and §43, they follow what the industry does, or are stricter. **Confirmed by the owner on 18 Nov 2026**; any of them can be reversed without touching the rest.

1. **Search through credits (16.2)** is one OpenRouter Chat Completions call with its **`openrouter:web_search` server tool**, engine **Exa** (the same price whichever model answers: $0.007 a search with up to 10 results), sent through our credits proxy, or straight to OpenRouter with the user's own OpenRouter key. A small, cheap model only lists what the search found; the results come back as `url_citation` annotations (address, title, excerpt). The deprecated `:online` suffix and web plugin are not used. OpenRouter's docs don't say whether search is inside `usage.cost`; **a real call showed it is** ($0.0076 = $0.007 search + $0.0006 tokens), so the credits proxy charges these calls as it charges every call (external-services.md).
2. **Search with the user's own key (16.3): Brave, Tavily and Exa**, called straight from the laptop, keys in the keychain like model keys and checked before saving. **Serper is dropped:** its terms describe its data as scraped and its service as business-to-business, and it resells Google's results pages, which §30 keeps us away from. Search in the browser on the user's request (16.4) is the browser tool (§43.4); search engines join the "forbids automation" list.
3. **One gate:** the search tool calls providers itself (the tool never holds a key or the device token), and the query is checked against the task's private passages first, like every web request (§43.5): a query carrying private content is refused before anything is sent. Every search is in the activity log with its cost, and **counts towards the task's budget** (16.12).
4. **Reading a page (16.5)** uses Mozilla **Readability** (Apache 2.0) on **linkedom** (ISC), falling back to plain text; pages that need JavaScript go to the browser tool. **Reading a whole site (16.6)** follows links on the same site, at most 25 pages, one request a second. Both **respect robots.txt** for our user agent `Titan117`; a page robots.txt closes can still be opened in the visible browser, as the user would.
5. **Cache (16.11):** the same search or page within 15 minutes isn't fetched or paid for twice, **in memory only** (nothing written to disk), per engine run. **Brave results are never cached**: Brave's terms allow keeping results only on a plan with storage rights.
6. **Trusted and blocked sites (16.9)** per agent: a "only these sites" list and a blocked list, passed to the search provider's domain filters and enforced when reading (a blocked site is refused). **Language and country (16.10):** a setting, from the laptop's own language by default, passed to Brave (`country`, `search_lang`), Tavily (`country`) and Exa (`userLocation`); OpenRouter's Exa search takes none, so the query's own language carries it.
7. **Deep research (16.8)** is a mode the user turns on for a task: a bigger budget (60 steps, 30 minutes, $2), instructions to plan the questions, search widely, read the best sources, cross-check, and finish with a **document artifact whose every fact has a numbered source**. Ideas from GPT Researcher (Apache 2.0); no code copied.
8. **Artifacts (17.1–17.7)** live in the local database, **a version for every change** (17.10), by the agent or by the user's own edit, which the agent then sees. Making or changing one **doesn't ask**: it is the agent's answer, every version is kept and restorable; saving one as a file in a folder (17.24) asks like any file write. Types: document (Markdown with tables), web page or small tool (HTML), spreadsheet (rows and columns), chart (data plus a chart type), diagram (Mermaid), slides (Markdown, one slide per section). Shown beside the chat in an **iframe with `sandbox="allow-scripts"` (no same origin) and a content policy with no network**: scripts only from our own bundled libraries, images only inline (17.18).
9. **Downloads (17.8, 17.19, 17.23)** are converted on the laptop in the app's own process: **PDF through Electron's own print to PDF** in a hidden window with no network and no Node (the feature map named Playwright's print: Electron is the same Chromium, with nothing extra to ship); **Word** with docx (MIT), real headings and tables; **Excel** with ExcelJS (MIT), real cells; **PowerPoint** with PptxGenJS (MIT), editable text; plus Markdown, HTML, plain text, CSV, the Mermaid source. A4 or Letter (17.20). Google Docs, Sheets and Slides (17.25) wait for the Google sign-in (§27).
10. **Share links (17.13, §30):** off until the user presses Share. The app makes a **self-contained snapshot** (the rendered page, no scripts from outside, no secrets: keys and tokens are refused, like any outgoing content) and uploads it with the device token; Convex keeps it in file storage with a `sharedArtifacts` row (an active plan required, at most 5 MB each, 100 shares and 30 a day per user). The link is `titan117.com/s/<id>` with a random id; **anyone with the link** can view it (chosen people come later, with sign-in). The page is served with a `sandbox` content policy, so it runs in an opaque origin with no access to our cookies; a separate domain for shared pages is planned before launch. **A Report button on every shared page** records a report (`shareReports`, with the reporter's email only if they give one), and staff take a page down from the product owner portal's admin function; the owner can unshare at any time, which deletes the snapshot.

11. **Licences:** Mermaid's optional ELK layout (elkjs) is EPL-2.0 or GPL-3.0, so it is **replaced by an empty stub at build time** and none of it ships; diagrams use Mermaid's own layouts. pako's "MIT AND Zlib" passes once Zlib, a permissive notice-only licence, joins the allowed list; two old MIT/X11 packages inside ExcelJS without an SPDX id are named exceptions.

12. **Searching in the browser on request (confirmed 18 Nov 2026):** besides `web_search`, the user can ask Titan to search on Google, Bing or another engine in the visible browser; Titan is told to use the browser for that search. Search engines are on the "forbids automation" list (asked once per site), a CAPTCHA hands over to the user, and it's one search at a time at a human pace, never background scraping (§29, §30).

**Against common practice:** server-side search tools, Readability, sandboxed iframes and print-to-PDF are what Claude, ChatGPT and Perplexity-style tools do. **Stricter than most:** robots.txt for single pages too, no disk cache, private passages blocked from queries.

## 48. Phase 5: keep awake, checkpoints and notifications

## 49. Phase 5: the Windows installer

## 53. Phase 7: the coding engine

Made on 20 Nov 2026 while starting phase 7 (features 5.7, §13). **Items 1 and 2 were decided by the owner on 20 Nov 2026; the rest are to be confirmed.** Checked against OpenCode 1.19.6's own source (`code/opencode` in the references folder, tag `v1.19.6`) and by running it.

1. **OpenCode ships unchanged, as its own program** (owner, 20 Nov 2026). OpenCode's code is MIT. Its program is built with Bun, whose runtime contains **JavaScriptCore, which is LGPL-2** (and tinycc, LGPL-2.1). LGPL is not GPL: an unchanged LGPL program may ship in a paid product with its notices and a link to its source, as Electron already does with Chromium's Blink and FFmpeg. The notices are in the desktop app's `SOURCES.md` and go into its licences file. **We may change it later:** OpenCode's own code is MIT, so we can change, fork and rebuild it and keep our changes private. Only changes to JavaScriptCore itself would have to be published, and we never need to make any. Improvements go in this order: its settings, then plugins and MCP tools, then our adapter around it, and a fork only if those aren't enough (a fork costs upkeep, since OpenCode releases often). Our lawyer's licence review before launch covers it.
2. **Downloaded the first time the code builder is used** (owner, 20 Nov 2026), not shipped in the installer:
   - OpenCode's program for the laptop's system (`opencode-windows-x64` and so on, version 1.19.6) from **npm, OpenCode's official channel**: about 80 MB to download, 213 MB on disk.
   - **ripgrep 15.1.0** (MIT or Unlicense, about 2.5 MB), which OpenCode would otherwise download from GitHub by itself.

   Both are **pinned and checked against hashes written in our code** (npm's sha512, ripgrep's published sha256) before anything is unpacked; a file that doesn't match is thrown away. They live in the app's data folder (`components/code`), never installed system-wide. After the download, the code builder works offline with local models. Not included yet: OpenCode's "baseline" builds for older processors without AVX2.
3. **One OpenCode server per coding task.** The engine starts it on 127.0.0.1 with a random password (requests without it are refused). It stops 15 minutes after the task's last message, so follow-ups continue the same coding session.
4. **Models through our bridge.** OpenCode is told about exactly one model provider: a small OpenAI-compatible server of ours on 127.0.0.1, with a token for that one task. Every model step goes through our model router, so:
   - credits, the user's own keys and local models work as for every agent;
   - each step is logged with its cost, and a coding job has its own budget (150 steps, $3);
   - a project in a local-models-only folder, or a task that read one, never reaches a cloud model (7.7);
   - offline, a cloud step stops with the offline note (§47).

   OpenCode holds no key.
5. **Our permission layer decides its asks**, with our approval screen, our activity log and our "always" answers. OpenCode is always answered "once", so it never remembers an "always" of its own.
   - **Reading, searching and listing** inside the project run at once (as our own file tools do); `.env` files are never read.
   - **Commands** follow the same rules as Titan's shell (§43.2): read-only ones run; the rest ask, with "always allow `<program>` in this folder"; the always-ask list always asks; and a networked command carrying private content is refused.
   - **File changes** ask, with "always in this task". Changes outside the project, in credential folders or in read-only document folders are refused even if approved.
   - **Refused outright:** its own web fetch and search (Titan does web work through the network policy), folders outside the project, its question and skill tools, language servers, and anything unknown.
   - **A step it keeps repeating** asks every time.
6. **Nothing of its own reaches the internet.**
   - **Switched off** by settings and flags, each checked in its source: updates, the model catalogue (models.dev), sharing, language-server and formatter downloads, plugins from npm, Claude Code's files, and the embedded web UI.
   - **Its own folders:** its config, data, cache and home folders sit inside our data folder, so the user's own OpenCode setup is never read or changed.
   - **Ignored settings:** the repo's (`opencode.json`, `.opencode/`) and the user's home (`~/.opencode`), so a repo can't widen its own permissions or load code.
   - **No npm installs:** on every start OpenCode installs its plugin helper from npm into its config folder. That folder is prepared so it finds the helper already there.
   - **Checked by the contract tests** (`pnpm test:opencode`, run on every OpenCode upgrade): they run the real program behind a recording proxy and fail if it reaches out at all.
7. **The commands it runs can't see its password.** They inherit OpenCode's environment, which holds its server password and the bridge token; with the password, a command could answer OpenCode's own asks. Our one plugin (a few lines that the engine writes into our data folder; no other plugin can load) blanks every `OPENCODE_` variable before a command starts. The contract tests check this, and they fail without the plugin. Otherwise commands get the shell's scrubbed environment (§43.1), with no keys or tokens. **On Windows its commands still run without an OS sandbox**, as Titan's do (§43.1); on macOS, running OpenCode inside Seatbelt is still to do in phase 7.
8. **The code builder starts as Titan's `code_task` tool.** Titan hands a coding job in a project folder (an allowed folder) to the engine, in "plan" mode (reads and proposes, 13.2) or "build" mode (changes files). Each command and change still asks. The next parts of phase 7:
   - its own screen, with diff review (13.3);
   - git, GitHub sign-in and pull requests (§25);
   - project memory, sub-agents and code review;
   - open in editor, and remote tasks;
   - other machines (3.15) and the user's own coding tools (13.14).
9. **Vendor terms, a first look on 20 Nov 2026** (from search results and secondary sources; each vendor's own pages are read before its part is built, guardrails §11b):
   - **OpenAI** started a program in September 2026 that lets ChatGPT plans be used in named partner tools. Titan117 isn't a partner, so Codex stays experimental, with an API-key mode (§20).
   - **Cursor:** its CLI and headless mode are its supported ways to run outside the editor. Its terms limit some uses, so it stays experimental too.

Still, we ask Modal in writing before building cloud sandboxes (owner checklist).

## 58. Phase 10: sidebar apps

Made on 22 Nov 2026 while starting phase 10 (features 6.2, 6.6, 6.11, 6.12, 6.14). **To be confirmed.** The projects' own licence files and the vendors' own pages were read on 22 Nov 2026 (guardrails §11b; rows in `external-services.md` and `open-source-references.md`). 1. **A sidebar app is a web app made with the app builder (6.2),** marked as one when it's made ("An internal tool for the Titan117 sidebar") or added later from the Apps screen. Only web apps: a mobile or desktop app runs on its own. Adding it writes three things into the app's folder and saves them as a version: the **`titan` SDK** (`src/titan.ts`, our own code), **`titan.json`** (its name, icon, the collections it keeps, and other apps' collections it reads or writes) and notes in its `AGENTS.md` telling the coding engine how to keep data.
2. **The shared data layer (6.11): one local database per app,** in the app's data folder (`sidebar-apps/<app>/data.db`), through Node's built-in SQLite (§38), out of every agent's reach like the rest of that folder. Records are JSON documents in named collections (`contacts`, `items`), each with an id and its times, so an app (or an agent changing it) never needs a migration. Filters by field, text search, sorting, 500 records a call at most; 256 KB a record, 100 collections and 200,000 records an app. Removing an app from the sidebar keeps its data unless the user ticks "also delete its data".
3. **What an app may reach is what the user agreed to.** Its own collections, always. Another app's collection only when `titan.json` names it (`"reads": ["inventory/items"]`, or `"writes"`), shown in plain words when adding it ("Read Inventory: items"); adding with anything else is refused. A new version that asks for more keeps the old build in the sidebar until the user looks again and agrees; one that asks for less loses it at once.
4. **Sandboxed, with no network.** The sidebar runs a **checked build**, never the working folder: adding or updating saves a version, runs the app's install, typecheck, build and tests, and copies `dist` into `sidebar-apps/<app>/builds/<version>` (the last three kept). The window serves it from `titan117://<app>.apps/` with a content security policy that allows only its own files (`connect-src 'none'`: no fetch, no websockets, no images or fonts from elsewhere), in a frame sandboxed **without same-origin** (no cookies, storage or access to the window, no pop-ups), which may never move to another address. The SDK talks only by messages to the window, which accepts them only from that app's own frame and passes them to the engine; the engine decides every call against item 3.
5. **Titan answers across the apps (6.11):** `sidebar_data` lists the sidebar apps with their collections, counts and field names, and reads records; reading doesn't ask (like memory), and what it reads is treated as private and as outside content (never instructions). `sidebar_change` adds, changes or deletes a record and asks each time (with "always" for the task). `sidebar_add` asks every time, on the laptop only, naming what the app may reach. The app's `titan.agent.ask("…")` puts a request in Titan's message box for the user to send; it never starts a task by itself.
6. **Agents maintain apps (6.14):** when `app_build` saves a version of a sidebar app that passes its checks, the sidebar gets it (the approved plan covers running it). An error inside a sidebar app is reported through the SDK and shown above it with **Fix with Titan**, which starts a task to fix it with the app builder. **Change with Titan** puts the app's name and folder in the message box.
7. **Sync (6.12) waits for the device keys of phase 15.** Every change is already written to a change log in each app's database. Sync between the user's own devices and team members will send those changes **end to end encrypted** through our cloud (§32), which holds only ciphertext and routing data (a planned table in §11). **Electric, Rocicorp's Zero and PowerSync are not used:** all three replicate from a server database that reads the data (Postgres or the user's backend), which §32 rules out, although their licences are Apache 2.0. **Evolu** (MIT, library and relay) works the way we need, relays that "store and forward encrypted changes they can't read"; it is our main reference, and its code may be reused under MIT when sync is built. cr-sqlite, Automerge, Yjs and TinyBase are MIT; Triplit is AGPL, Twenty AGPL (its CRM is ideas only) and NocoDB fair-code (ideas only).

12. **The sync core, built 22 Nov 2026 (6.12):** every change to a record is logged, and a deletion is remembered (a tombstone), so another device can't bring it back with an older copy. A **sync package** holds one app's changes since the last one sent, each record as it is now; it's sealed with **AES-256-GCM** under the account's 32-byte sync key, the app's name and every field inside the ciphertext, padded to a multiple of 1 KB; anything changed or sealed with another key is refused. The receiving laptop merges **last-writer-wins** per record (a later edit is always later than the last one on that laptop; the same millisecond is settled the same way everywhere), accepts only apps in its own sidebar, checks every record like its own, and doesn't send merged changes back. **Waits for phase 15:** sharing the sync key between the user's devices (with their device keys) and the relay in our cloud (the planned `syncChanges` table, §11), with its own access control (Evolu's relay admits anyone who knows an owner id).

## 59. Phase 11: the agent builder

Made on 22 Nov 2026 while starting phase 11 (features 4.1–4.4, 4.6, 4.7, 2.4, 2.7, 2.8, 18.1, 18.2). **To be confirmed.** The projects' licence files and OpenRouter's own pages were read on 22 Nov 2026 (guardrails §11b; rows in `external-services.md` and `open-source-references.md`). Phase 11's check: a user creates an agent in the form; a manager agent splits a task between two agents; Titan builds a new agent and its skills from a request.

1. **An agent is a file (4.1):** `agents/<id>.md` in the app's data folder: a short header (name, one-line role, team, colour, model and fast model, tool groups, memory, whether it hands out work, tools that always ask, skills) and the agent's instructions as Markdown underneath. The same shape as Claude Code's sub-agents, CrewAI's agents (role, goal, tools) and the OpenAI Agents SDK's agents (instructions, tools, handoffs); our own code, nothing copied. The data folder is out of reach of every agent's file tools, like skills (§43.7): a file changes only through the Agents screen or `agent_create`, which asks. Unknown tool groups, bad names and over-long instructions are refused when the file is read or saved. An agent's name never changes (it is its memory scope); clone to rename. Trusted and blocked sites per agent stay in Web search (16.9), keyed by the agent's name.
2. **Built-in agents (4.2)** live in our code, can't be changed or deleted, and are updated with the app: **Titan** (every tool), **Researcher** (web search and reading, reports with sources), **Writer** (documents, offers, emails, artifacts; no shell or browser), **Folder agent** (the user's documents, cited by file and page) and **Builder** (code and apps). Phases 12–14 add the QA, SEO, marketing and video agents the same way. **Clone and edit (4.3)** copies one into a file of the user's, under a new name.
3. **A definition only narrows (§21).** An agent gets the tools of its groups and nothing else; each call still goes through the permission layer with the same asks, budgets and network policy. "Always asks" in a file can make a tool ask that normally runs at once (or never take "always"); nothing in a file can make anything ask less. Instructions are added below our own fixed rules, never in place of them. Agents still never write to the core (§21).
4. **Memory (4.7):** an agent reads shared memory and its own (§43.6), or with "own memory only" just its own; what it saves is shared unless it says otherwise, so the team learns from each other. Skills listed in the file are offered to it first.
5. **Agents working together (4.6):** any agent with `agent_delegate` (Titan, and an agent the user marks as a manager) hands a part of a task to another agent with a clear brief. Each part is **its own task, linked to the first** and shown under it, run with that agent's file, its own approvals and activity; the answer comes back to the manager as the tool's output, marked as data. Several parts in one step run at the same time, **at most three**; **one level deep** (a helper can't hand on); a part's cost counts towards the first task's budget. Ideas from CrewAI's hierarchical crews and the OpenAI Agents SDK's agents-as-tools (both MIT), our own code.
6. **The message bus (4.7)** is a local table (`agent_messages`, in the laptop's database) of messages between agents in one piece of work: who wrote to whom, the brief, the answer, when. The task's details show it as "Team talk". Local only (§32).
7. **Smart routing (2.4):** an agent (or the Models screen for Titan) may name a cheaper **fast model** next to its main one. The main model takes the first step of every turn (the plan) and any step after a failed tool call; the fast model takes the rest. Off unless a fast model is chosen; the activity log says which model took each step.
8. **Compare models (2.8):** the same prompt on up to four models side by side, with no tools, showing each answer, its time and its cost; the estimated cost shows first. Nothing is kept. The prompt leaves the laptop only for cloud models, as for a task.
9. **Agents and skills on request (18.1, 18.2):** `agent_create` lets Titan write a new agent's file and the skills it needs; **one approval card** shows the name, team, tools, sites and each skill's steps, every time, on the laptop only (a new agent is a standing instruction, like a skill). The agent then appears in the sidebar under its team.
10. **Media (2.7), built 22 Nov 2026 (see item 13):** images through OpenRouter's **Images API** (`POST /api/v1/images`, `usage.cost` in the answer, "Failed or cancelled generations are not billed") and video through its **Videos API** (asynchronous: a job, polled every 10–30 seconds, downloaded with the key; `usage.cost` on the finished job), both through our credits (§33.5) once the proxy forwards them, or the user's own OpenRouter key. Speech output through OpenRouter needs streaming Chat Completions with `modalities: ["text", "audio"]`; the system voices stay the default (§43.10). Video's zero-data-retention isn't supported, so the card says the prompt is kept by the provider. fal.ai and Replicate stay the user's own accounts (§31).
11. **Built 22 Nov 2026 and seen working in the built app** (Claude Haiku 5.5): an "Invoice clerk" made in the form totalled `invoices.csv` per client with only its file and memory tools; Titan handed a research part to Researcher and an email to Writer at the same time and put both together ($0.02 for the parts); Titan made "Supplier chaser" in Operations with a `late-delivery-reminder` skill after one approval with no "Always"; Compare ran Claude Haiku 5.5 next to another model. That is phase 11's check. Tool groups follow what each tool declares (a new tool can't slip past a definition); scripts an agent runs (4.10) have only that agent's tools.
13. **Media, built 22 Nov 2026.** `image_create` and `video_create` (tool group "Images and video") save the result as a file in an allowed folder (`images/…`, `videos/…`, or the path asked for). Both cost money, so both ask: an image with "always in this task", a video every time and on the laptop only. The prompt is checked for private content before anyone is asked, like a web request. The models are a setting on the Models screen ("A common one, chosen for you" by default, from OpenRouter's public list). **The credits proxy** got `POST /api/v1/images` (charged at `usage.cost` once the image is back, nothing when it fails) and video jobs: `POST /api/v1/videos` keeps the job's id on its `proxyCalls` row (a new `jobId` field), `GET /api/v1/videos/{id}` and `/content` answer only the job's owner (anyone else gets "not found"), and the job is charged once when it ends (nothing for failed, cancelled or expired). A caller can't set OpenRouter's webhook address. **Open:** a job nobody polls to the end isn't charged; before production the proxy should also take OpenRouter's signed webhook (`callback_url`, `X-OpenRouter-Signature`) so every job is charged. Some image models ignore the file type asked for (Gemini's answers JPEG), so the agent says so instead of renaming the file.
12. **Not used:** n8n (fair-code) and the `packages/ee` parts of Activepieces and the `ee/` folders of Mastra (commercial); the Claude Agent SDK's TypeScript package is under Anthropic's commercial terms, so ideas only. AutoGen is archived (its successor is Microsoft's Agent Framework).
